## D-001 — Технологический стек бота

**Дата:** 2026-03-04  
**Статус:** accepted

### Контекст

Нужен Telegram-бот для генерации `.ics`, позже — шаблоны в БД. Основной стек пользователя — TypeScript, IDE — WebStorm.

### Решение

- Runtime: **Node.js**
- Язык: **TypeScript**
- Telegram framework: **Telegraf**
- Валидация: **Zod**
- ORM/DB слой (когда подключим): **Prisma + PostgreSQL**
- Тесты: **Vitest**

### Причины

- Быстрое MVP и понятная структура без тяжёлых фреймворков.
- Telegraf удобен для будущих wizard/flows.
- Prisma даёт строгую типизацию и удобные миграции.
- Zod закрывает runtime-валидацию пользовательского ввода.

### Последствия

- Проект строим как сервис (бот), без web UI / OpenAPI.

## D-002 — Режим получения апдейтов Telegram

**Дата:** 2026-03-04  
**Статус:** accepted

### Контекст

Нужно вывести бота в прод. Возможны два режима: long polling или webhook.

### Решение

На первом релизе используем **long polling**.

### Причины

- Проще инфраструктура (не нужен публичный HTTPS endpoint).
- Отлично подходит для VPS, где процесс бота постоянно запущен.

### Последствия

- Позже можно перейти на webhook без изменения бизнес-логики.

## D-003 — ESM и настройки TypeScript

**Дата:** 2026-03-04  
**Статус:** accepted

### Контекст

Нужно современное окружение без лишней магии, совместимое с Node 22.

### Решение

- `package.json`: `"type": "module"`
- TypeScript: `module: "NodeNext"`, `moduleResolution: "NodeNext"`
- Разделяем конфиги:
  - `tsconfig.base.json`
  - `tsconfig.json` (dev/typecheck, noEmit)
  - `tsconfig.build.json` (emit в dist)
  - `tsconfig.eslint.json` (на будущее для type-aware lint)

### Причины

- Предсказуемая работа ESM в Node.
- Удобство CI и сборки.

### Последствия

- Следим за корректными импортами (ESM).

## D-004 — Отказ от alias импортов

**Дата:** 2026-03-04  
**Статус:** accepted

### Контекст

Alias `@/*` часто требует доп. настройки резолва в рантайме.

### Решение

На старте **не используем alias**, только относительные импорты.

### Причины

- Максимальная простота продакшена: “что в dev, то и в prod”.

### Последствия

- Важно держать неглубокую структуру папок, чтобы не утонуть в `../../`.

## D-005 — Стандарты репозитория и quality gates

**Дата:** 2026-03-04  
**Статус:** accepted

### Контекст

Нужно качество и повторяемость окружения (как в FE-шаблоне).

### Решение

- Package manager: **pnpm (corepack)**, запрещаем yarn/npm через `only-allow`
- Prettier + ESLint
- Husky + lint-staged
- CI (GitHub Actions): format, lint, typecheck, tests, commitlint
- Скрипт: `scripts/check-lockfiles.cjs` оставляем

### Причины

- Быстро ловим ошибки до мержа.
- Одинаковый стиль и правила в команде/на разных машинах.

### Последствия

- Любые изменения в tooling должны проходить CI.
